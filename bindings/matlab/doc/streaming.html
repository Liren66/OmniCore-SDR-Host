Streams, Full Duplex, and Dropped Samples

How receive and transmit share one device, and how dropped samples are reported

One RX stream and one TX stream per device

DirectionOperations that hold this stream
RXreceive (during the call), a running RxStream, Receiver (from the first call until release)
TXtransmit (during the call), transmitRepeat (until stopTransmit), an active TxStream (from the first write until stop), Transmitter

A second operation on the same direction at the same time raises omnicore:BUSY. RX and TX can run at the same time (full duplex).

Full-duplex start/stop rules

Once either stream has stopped, a new stream can only be opened when both directions are stopped. In other words, while TX is transmitting, RX can be started once, but once stopped it cannot be started again; the same applies the other way round. Violating this raises omnicore:BUSY ("stop both directions before reopening a stream").

The reason is that the core only resets the USB pipes when both directions are stopped. In practice:

  • For full-duplex measurements, use one RxStream (or Receiver) that keeps running paired with a TxStream (or Transmitter), rather than calling receive for each measurement.
  • Cut out the parts you need from the running RX stream by hardware timestamp; see the examples video_link and timed_burst_loopback.
  • When you need to switch to a different approach, stop both directions first (stop, stopTransmit, release).

RX and TX in one loop

dev = omnicore.Device('RxChannels', 1, 'TxChannels', 1, 'TxGain', 20);
rx = rxStream(dev); tx = txStream(dev);
start(rx);
write(tx, complex(zeros(0.1 * dev.SampleRate, 1, 'single')));   % 100 ms of headroom
for k = 1:1000
    write(tx, make_block(k));          % returns immediately (when the buffer has room)
    [y, meta] = read(rx, 122880);      % waits for the device: the loop runs at the sample rate
    process(y);
end
stop(tx); stop(rx);

read waits for data from the device, so the loop naturally runs at the sample rate; the block of zeros written first keeps TX ahead of the loop, so an occasional MATLAB stall does not cause underflow. The Latency property of omnicore.Transmitter does the same thing.

RX dropped samples

The device writes samples continuously into the host ring buffer (64 MiB by default); samples are only dropped if the buffer fills between two MATLAB reads. Drops are reported exactly:

  • meta.Overflow is true;
  • each row of meta.Gaps is [row, count]: how many samples are missing before that row (computed from hardware timestamps); samples dropped between two read calls are recorded in row 1;
  • lost samples are not zero-filled; the array contains only the samples actually received, and the timestamp meta.TimeTicks refers to the first sample.

To avoid drops: increase BufferBytes; reduce per-block processing and plotting (drawnow limitrate, plot only every few blocks); at high rates, capture everything at once with receive and process afterwards.

TX underflow

When the device has no samples to send in the middle of a burst, Underflow is reported (in the output of status / Transmitter); this is an interruption on the RF side. Starved only means the host queue was temporarily empty: it also appears while a timed burst is waiting for its start time, where it is harmless.
